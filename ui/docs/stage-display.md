# ステージDBの表示と共通設定

## 画面とデータの流れ

- ステージ詳細 `/pages/stage-detail/?map=N000` の上部にある「表示」で通常・詳細を切り替える。再アクセス時は通常で始まる。冠は各ステージ名の横に置き、全ステージで共有する。敵ステータスは独立した設定。旧詳細列の `details` は読み込まない。
- `display-data.js` の `loadStageDisplayMap` は検索索引と選択マップの詳細を照合し、敵・キャラ索引とともに返す。候補を切り替えたときは既存の `loadStageVariant` で1面だけを差し替える。冠・表示モード・編集プレビューでは取得済みのマップを使用する。
- `display-fields.js` はゲームデータを登録済みの表示項目へ渡す。`display-raw.js` は正式列名と元の位置を対応させる。既存の `view.js` の出撃準備用入口と、出撃制限、特殊ルール、EX、報酬画像、固定編成の組み立てを共用する。
- `display-sheet.js` の `mountStageSheets` は実ページとエディターで使用する。ステージごとに見出し、基本、メディア、報酬、出典、敵の行グループを持つ。DOMが同じ場合は差し替えを省き、冠や表示モードの変更で背景・BGMを作り直さない。元データを見ている場合は折りたたみ状態を復元する。
- XP・素材・報酬判定は既存の `calculateNative` へ送り、入力が同じ結果を共用する。敵のステータスは既存の `prepareEnemyStatistics` で準備する。描画リビジョンを照合し、旧冠や旧候補の結果が現在の表示を更新しないようにする。保存画像は表示中のモードのシートを対象にし、敵表のスクロール幅を保存用の複製だけ広げる。

## 標準設定とプリセット

標準のラベル・順番・表示条件・幅・説明・揃え・強調は [display-defaults.json](../src/features/stages/display-defaults.json) に置く。ステージ詳細上部の「表示設定」、または設定の「見た目」から `/pages/display-settings/` を開ける。検索して選んだ実ステージを、冠・通常/詳細・秒/F・敵ステータスを変えながら確認できる。

`display-settings.js` の `displayConfiguration` はレジストリ初期値、標準JSON、個人差分を順に適用する。個人設定は `kbcs:database-display:stages` に保存する。`schemaVersion: 1`、`database`、`activePresetId`、`presets` を持ち、各プリセットは ID・名前・変更属性 `overrides`・グループ内順序 `orderOverrides` を保持する。標準プリセットの ID は `standard`。表示モードの通常/詳細はこの保存領域に含めない。

標準値に戻した属性は個人差分から外す。未指定の項目は標準順で最も近い先行項目の直後に挿入し、個人が並べた項目の相対順を保つ。同順は ID で決める。廃止項目は警告を表示して読み飛ばす。改名は `aliases` で対応し、`stage.maxEnemies` は `stage.enemyLimit` へ移行する。設定が破損している場合は標準で開く。

エディターの「保存」で個人設定を確定し、「取消」で最後の保存状態に戻る。JSON入出力では個人設定一式、単体プリセット、開発者標準を選ぶ。開発者モードで出力したJSONをレビューし、標準ファイルを差し替える。書き出し順は ID 順。時間系の表示単位は、レジストリで許可した秒/F/画面指定から選べる。

## キャラ・敵DBへの適用

対象DBのレジストリと標準JSONを用意し、`displayConfiguration` に DB ID、フィールド群、標準設定を渡す。フィールドは固定ID、グループ、値取得関数、許可する整形を持つ。`data-sheet.js` の `sheetRows` は値の採否を判定してから2組ずつ配置し、余りは全幅になる。`columnTable` は有効なレコードの有無を列単位で判断する。DB固有の複合ブロックは `sheetRow` に渡す。実ページとエディターの双方から同じ表示アダプターを呼ぶ。

画面に渡す値は text、登録済みレンダラーが生成したHTML、欠損等の状態のいずれか。エディターが扱うラベル・説明はプレーンテキスト。`sourceOnly` は詳細の出典へ、`whenActive` は通常表示で有効値だけを表示する。状態には未収録・無効・対象外・未確認・未対応がある。罫線と行構造は共通の `data-sheet.css` が管理する。

設定画面、JSON、CSS、JSは既存の `include_dir!` から配信する。`sync-ui.py` は上流を読み取り専用で扱い、ステージ側のJS・CSSを保持して共通依存をたどる。このページと共通設定のファイルは上流コピーの対象外。

116列の対応と挙動の検証境界は [列対応台帳](../../crates/kbcs-data/docs/stage-columns-v3.md) を参照。

## 確認結果

- v3 JSON、CSV、表示対応表で116キー・同一スコープ内の正式名・列番号・等級・根拠を突き合わせた。JSON・JS・ローカル配信パス、同期保護設定、UTF-8 BOM、表示基盤のNodeテスト3件を確認した。
- 既存のJP 15.7.4データと既存ローカルAPIを用い、Chromiumで N000・PR000・G002・D000 を確認した。通常と詳細の切替、4冠の同期・再アクセス、敵ステータスの独立、素材の入手確率、固定編成、候補選択、イベントPtと固有条件を確認した。1280pxと320pxで確認し、320pxでは濃紺・ダーク・ライトの各テーマで敵表だけを横スクロールできた。320pxからのステージ画像保存は944×1524pxのPNGになった。
- エディターで実データのプレビュー、編集・取消・保存、プリセット複製・改名、実ページへの適用、個人設定JSONの書き出しと再取り込み、未対応版JSONの拒否、開発者標準の書き出しと秒/F設定を確認した。
- `kbcs-data` は既存依存を再利用してテストコードを含めて型検査した。Windows環境のclang未検出と代替リンカーの異常終了により、新しいRustテストバイナリと配布版は未実行。次回のビルド環境では `cargo test -p kbcs-data map_options_keep_new_columns_and_legacy_annotation` と、新しい詳細APIにおける20列の旧版・21列の新版の原本参照を確認する。全体ビルド、全アセット再取り込み、ネイティブの追加解析は今回の検証範囲外。
